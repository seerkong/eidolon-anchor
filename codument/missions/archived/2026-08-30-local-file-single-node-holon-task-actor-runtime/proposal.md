# Mission: Local-file single-node Holon task actor runtime

## Why now

The project family already contains three substantial but disconnected bodies of work:

- Holon Workbench owns effective-dated OrganizationalSubject, Holon, Member, Membership, Role, Assignment and Policy master data.
- depa-flows owns Definition → Instance → Run authority, Ctrl/Data AI Workflows, StepSpace and an early `task-manager-*` runtime.
- Eidolon owns generic Agent actors, actor snapshots/sessions, ResourcePackage-backed `AIAgentDefinition`, and durable workflow execution.
- depa-actor owns the reusable in-process Actor/Processor substrate intended to keep actor semantics out of individual products.

Current integration facts are split across independent stores and types. A workflow can address an `AIAgentDefinition`, but cannot yet delegate a complex node to a frozen Holon organization that owns an independently managed TaskSpace. Eidolon's historical Holon/team/task facts are also not a safe replacement for Holon Workbench or `task-manager-*` authority.

## Desired outcome

Deliver the first, deliberately bounded system version:

1. Holon Workbench remains human/machine-neutral organization master data.
2. Holon Workbench signs a portable exact effective snapshot Resource/receipt; Task creation freezes it into `HolonTaskSnapshotReceipt`, and later organization changes do not alter the running task without explicit replan.
3. An Eidolon `HolonExecutionBinding` Resource maps frozen Member/Role references to a closed AI/human endpoint/service/hybrid execution adapter and runtime policy without changing Holon core models or routing from `principalKind`.
4. A complex Ctrl/Data workflow node can create or reference an independent TaskSpace and target a Holon organization.
5. A single Eidolon deployment hosts several Holons and Members. Each `(deploymentId, holonRef)` has a shared HolonRuntime/Coordinator that assigns ready organization tasks; each `(deploymentId, memberRef)` reuses one long-lived `MemberRuntime` by default, while explicit isolation creates a bounded temporary runtime. Runtime reuse does not implicitly share conversation: default session scope is the exact task claim attempt, with explicit targeted Agent-instance continuity only.
6. Member runtimes use depa-actor's local substrate and Eidolon's generic actor/session authority rather than introducing a workflow-specific actor system.
7. All durable authority uses recoverable local files. Cross-machine actor routing, database storage, RabbitMQ, actor placement and node/placement leases are reserved for Mission 2; local TaskSpace claim heartbeat/expiry remains part of Mission 1.
8. The real File-XNL E2E organization has a deterministic, repository-owned inspection resource that can be regenerated byte-for-byte without becoming a product runtime authority.

## Scope

This mission coordinates eight pending Tracks across four repositories:

- Holon principal/effective snapshot model.
- TaskSpace kernel/file owner.
- depa-actor local logical addressing.
- Holon governance/store seam refactor plus SQLite and XNL adapters.
- HolonExecutionBinding resource authority.
- AI Workflow Holon task target profile.
- Eidolon single-node MemberRuntime.
- Product-level Ctrl/Data E2E.

The mission includes minimal patch releases and exact dependency updates when implementation Tracks require them. Publishing must not pass a registry argument or add a registry override to package metadata or npmrc.

## Non-goals

- No RabbitMQ or other transport.
- No remote actor reference, cluster membership, actor placement, node/placement lease or ownership epoch. This does not exclude the local TaskSpace claim lease/expiry protocol.
- No database-backed authority in the Mission 1 deployment/E2E; preserving the existing Holon SQLite adapter for conformance and one-way import is compatibility work, not a second runtime owner.
- No changes to Codument TaskSpace.
- No `AIAgentDefinition` field in Holon Workbench core entities.
- No automatic mutation of in-flight task organization snapshots.
- No dual writes between SQLite/XNL, legacy Eidolon facts and the new canonical owners.

## Success criteria

- A local ResourcePackage can carry the complete versioned Holon organization closure and bind it to exact AI/human/service/hybrid adapter resources.
- Ctrl and Data workflows both delegate a complex node to a TaskSpace owned by that snapshot.
- Multiple Holons/Members run in one Eidolon process through stable logical actor addresses.
- Repeated member calls reuse the same shared MemberRuntime unless isolation is explicit, while unrelated tasks default to distinct generic sessions and explicit by-id/by-name selection reuses an admitted Agent instance.
- Restart recovers actor, workflow, TaskSpace and organization references without live-source rereads.
- Organization revision drift is ignored by an existing task until explicit replan creates a new frozen snapshot and receipt.
- Static and runtime gates demonstrate a single authority per fact class and no Mission 2 code path.
- A checked-in E2E inspection directory exposes the real File-XNL physical layout and issuer projections, while an isolated regeneration gate proves it matches the same capsule write/reconstruct/issue path and contains no host-local paths or runtime-private history.

## Risks

- Treating projections as authority would create multiple writable copies of organization, task or actor state.
- Freezing only identifiers, rather than exact effective records and resource closure, would make restarts depend on live sources.
- Cross-owner file updates cannot be made truly atomic; the design therefore uses durable receipts plus CAS handoff instead of pretending there is one transaction.
- A shared MemberRuntime can leak context if addressing and task/session scoping are not closed and explicit.
- Package ownership can drift unless each Track keeps pure contracts/logic separate from filesystem and product adapters.
