# Design: Inspectable File-XNL Holon E2E resource

## 1. Authority boundary

The generated directory is immutable inspection/test evidence. It is not opened as the product's writable organization owner and is never admitted as a substitute for the live capsule write performed by the product E2E. Tests prove both paths separately:

- product E2E: new temporary authority → commit → fresh issuer → ResourcePackage;
- inspection gate: deterministic scenario → explicit empty candidate root → commit → fresh issuer → compare the complete output to committed bytes.

## 2. Layout

```text
tests/resources/holon-task-e2e/
  README.md
  manifest.json
  authority/
    head.xnl
    records/<sha256>.xnl
    trees/<sha256>.xnl
    receipts/<revision>.xnl
    transactions/
    projections/
  issued/
    holon-effective-snapshot.json
    issuance-receipt.json
```

`authority/` is the real File-XNL owner layout. `issued/` and `manifest.json` are derived, explicitly labelled read artifacts. The manifest records only logical ids, fixed scenario instants, revisions and digests; it never records the output root.

## 3. Processor shape

The effectful materializer follows the direct DEPA form:

```ts
output = materializeFileXnlHolonE2eResource(runtime, input, config)
```

- `runtime` owns directory creation, regular-file writes and the real capsule issuer operation.
- `input` carries the explicit output root.
- `config` carries the closed deterministic scenario.
- output contains logical provenance/digests and written relative paths, never the absolute root.

The executable wrapper binds Node filesystem effects and the actual `HolarchyFileXnlCapsule`. It rejects a non-empty output root rather than deleting or overwriting unknown files. Arrays and record keys use explicit UTF-16 code-unit ordering.

## 4. Determinism and check

The scenario uses fixed logical ids and instants. The check materializes into a fresh temporary root, recursively validates regular-file/no-symlink boundaries, compares the exact relative path set and every byte against the committed directory, and then reconstructs the capsule and parses the issued snapshot/receipt.

The committed README is excluded from generated byte comparison because it is explanatory documentation; every other file is generator-owned. Any drift fails the focused test and the package script.

## 5. Security and privacy

Static and runtime checks reject absolute host paths and runtime-private vocabulary/content. The resource contains no prompt, reasoning, provider configuration, actor snapshot, mailbox or conversation history. Content-addressed filenames and receipts remain canonical output from Holarchy packages.

## 6. Compatibility

No public product API, persisted product schema, dependency version or package publication changes. Existing tests may import the scenario facts to remove duplicate literals, but their temporary owner lifecycle remains unchanged.
